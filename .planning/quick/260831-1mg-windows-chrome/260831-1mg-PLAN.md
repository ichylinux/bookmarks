<objective>
Fix the task gadget header 追加 button never appearing on hover under Windows + Chrome.

Purpose: The reveal is gated on media features that describe only the *primary* pointing device. On Windows machines with a touchscreen (2-in-1s, Surface, most current Windows notebooks) Chrome reports the touchscreen as primary, so a mouse user gets `hover: none` / `pointer: coarse` and the button stays at `opacity: 0` with `pointer-events: none`. Non-touch macOS/Linux machines report the mouse as primary, which is why the bug is invisible to the developer.

Output: Two widened media conditions in `welcome.css.scss`, a red-first Cucumber scenario that locks the desktop hover contract (currently untested — every existing step reaches the link with `visible: :all`, which is precisely why this shipped), and a human confirmation on the reporter's Windows machine.
</objective>

<root_cause>
Verified by reading the source, not inferred:

Header markup is `app/views/common/_gadget_title_with_icon.html.erb` line 3:
`<div class="title title--gadget-with-icon" data-gadget-icon="todo">`, so the reveal selector `div.title:hover` does match the element the user hovers.

Two blocks in `app/assets/stylesheets/welcome.css.scss` gate the reveal:

- **Line 321** — inside the shared `.bookmark-gadget-new-link, .todo-gadget-new-link, .feed-gadget-settings-link` block (which sets `opacity: 0`), a nested media query applies `pointer-events: none` when the primary pointer cannot hover.
- **Line 375** — the reveal block `div.title:hover .{bookmark-gadget-new-link,todo-gadget-new-link,feed-gadget-settings-link} { opacity: 1; pointer-events: auto; }`, gated on the primary pointer being both hover-capable and fine.

The CSS `hover` and `pointer` media features report **only the primary input mechanism**. Chrome on Windows treats an available touchscreen as primary on touch-enabled laptops, so on such a machine — even with a mouse plugged in and in active use — the line 375 block never matches (button stays `opacity: 0`) and the line 321 block does match (`pointer-events: none`). That is exactly the reported symptom, and exactly why it reproduces on Windows + Chrome and nowhere else.

The correct features for "can *any* attached input mechanism hover / is *any* attached pointer fine" are `any-hover` and `any-pointer`. Under those:

| Device | any-hover | any-pointer | Reveal on hover? |
|---|---|---|---|
| Windows touchscreen laptop + mouse | hover | fine | yes (bug fixed) |
| macOS/Linux desktop | hover | fine | yes (unchanged) |
| Phone | none | coarse | no (unchanged) |
| iPad, no pointer, landscape >767px | none | coarse | no (unchanged) |

**Why this cannot re-break the mobile regressions** (STATE.md quick tasks 260710-p6v and 260712-j75, code comment QUICK-MOB-ADDBTN-02): inside `@media (max-width: 767px)` the hide rule `.gadget.todo .title--gadget-with-icon .todo-gadget-new-link` has specificity (0,4,0) and the reveal rule has (0,3,1); (0,4,0) wins regardless of which media feature gates the reveal. Only the media *condition* changes here — never a selector — so that ordering is preserved.

**Deliberately out of scope:** `welcome.css.scss` line 213 (`#bookmark_gadget .folder-header` hover background) and `preferences.css.scss` line 45 use the same primary-only features, but they only suppress a cosmetic highlight — the controls stay fully visible and clickable on Windows. No functionality is lost, so they are left alone to keep this quick task atomic.
</root_cause>
