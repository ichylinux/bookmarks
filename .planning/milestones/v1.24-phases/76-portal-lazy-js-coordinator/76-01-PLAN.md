Required top-level structure (executes at Sprockets bundle parse time, BEFORE any `$(document).ready`):

1. File header comment: same one-line "Sprockets bundle: share namespace for load order (no new globals)." style used in `todos.js` line 1.

   - `const portalLazy = window.portalLazy;`
3. A single IIFE `(function() { ... })();` that encloses ALL internal state and helpers and then attaches the two public methods to `portalLazy`.

Inside the IIFE, in this exact order:

a) Local helper `isMobileViewport` — VERBATIM duplicate of the `portal_mobile_tabs.js` lines 4-7 implementation (same 767px breakpoint, same `function` keyword, same `if (!window.matchMedia) return false;` early return). Do NOT use a different breakpoint, do NOT use a custom comparison.

b) Read the initial column index from the CSS custom property at parse time:
   - `const rawIndex = document.documentElement.style.getPropertyValue('--portal-initial-active-index');`
   - `const parsed = parseInt(rawIndex, 10);`
   - `const initialColumnIndex = (Number.isNaN(parsed) || parsed < 0) ? 0 : parsed;`
   - The NaN-and-negative guard is mandatory (see Pitfall 2 in RESEARCH.md). Do NOT omit it.
   - `initialColumnIndex` is internal — DO NOT expose it on `window.portalLazy` (CONTEXT.md locked decision).

c) Internal state containers using `const` (these objects are mutated, but never reassigned):
   - `const queues = {};` — keyed by columnIndex (integer), value is array of pending `loadFn` references
   - `const loadedColumns = {};` — keyed by columnIndex, value is `true` once that column has been loaded

d) Public method `portalLazy.register = function(columnIndex, loadFn) { ... };` with this exact branching contract:
   - If `isMobileViewport()` returns false → call `loadFn()` immediately and return. This satisfies DESKTP-01 (desktop pass-through, zero behavior change).
   - Otherwise (mobile path):
     - `queues[columnIndex] = queues[columnIndex] || [];`
     - `queues[columnIndex].push(loadFn);`
     - If `columnIndex === initialColumnIndex` → call `portalLazy.loadColumn(columnIndex);` so that registering a loader for the initial active column drains it immediately (satisfies LAZY-01 for the initially active column).

e) Public method `portalLazy.loadColumn = function(index) { ... };` with this exact ordering:
   - First statement inside the function body: `if (loadedColumns[index]) return;` — early return for already-loaded column (satisfies LAZY-03).
   - Immediately next statement: `loadedColumns[index] = true;` — MUST be set BEFORE the loop that invokes any `loadFn`. This is the synchronous mark-before-fire contract (IMPL-04, see Pitfall 3 in RESEARCH.md). DO NOT move it to a callback. DO NOT move it after the loop.
   - Then: `const fns = queues[index] || [];`
   - Then a `for (let i = 0; i < fns.length; i++) { fns[i](); }` loop that invokes each queued function once. Use `let i`, not `var i`.

Forbidden patterns (will fail acceptance):
- Wrapping the whole module body inside `$(function() { ... });` or `$(document).ready(...)` — this delays init past parse time and breaks Phase 77 wiring (Pitfall 1).
- Using `var` anywhere (ESLint `no-var` will fail).
- Reading `localStorage` directly for the initial column index (CONTEXT.md decision: use the CSS custom property, not a second localStorage read).
- Exposing `initialColumnIndex`, `queues`, `loadedColumns`, or `isMobileViewport` on `window.portalLazy` (only `register` and `loadColumn` are part of IMPL-01).
- Renaming the file to anything other than `portal_lazy.js` (alphabetical Sprockets load order matters — see Pitfall 4).
- Adding `//= require` directives in `application.js` for this file (it is picked up automatically via `require_tree .`).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Inline prehydration `<script>` in `_dashboard.html.erb` → Sprockets bundle (`portal_lazy.js`) | The prehydration script writes a CSS custom property (`--portal-initial-active-index`) read by `portal_lazy.js` at parse time. Both run in the same origin / same page context, but the IIFE in the dashboard view is authored by the application (not user input). |
| `window` global object → other Sprockets modules / future Phase 77 partial code | `window.portalLazy` is added to the global namespace; any other script can read or overwrite it. The `|| {}` namespace guard partially mitigates accidental double-init. |
| `loadFn` parameter passed into `portalLazy.register(columnIndex, loadFn)` | In Phase 76 nothing calls `register`. In Phase 77, gadget partials (server-rendered ERB) will pass closures created from app code, not from user input. Trust origin: same application; not externally controllable. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-76-01 | Tampering | `window.portalLazy` global | accept | Browser-side global namespace is by design; other first-party Sprockets files may read it. Risk of malicious tampering = risk of attacker-controlled JS execution, which is already a higher-level concern (Rails escapes ERB output; no `unsafe-inline` user content reaches the JS bundle). No PII or auth tokens are touched by this module. |
| T-76-02 | Injection (loadFn execution) | `portalLazy.register(columnIndex, loadFn)` invocation site | mitigate | In this phase no caller invokes `register`. In Phase 77 the only callers will be hand-authored gadget partials passing closures (not strings, not `eval`, not user input). This phase introduces NO `eval`, NO `Function(...)`, NO `new Function`, NO `setTimeout`/`setInterval` with string arguments — verified by the absence of these tokens in the file. |
| T-76-03 | Injection (columnIndex) | `portalLazy.register(columnIndex, ...)` / `loadColumn(index)` indexing | mitigate | `columnIndex` is used only as an object property key (`queues[columnIndex]`, `loadedColumns[index]`). It is never concatenated into HTML, never passed to `eval`, never used as a selector. JavaScript object property access does not enable XSS even if `columnIndex` were attacker-controlled. The phase 77 caller will pass server-side integer indices. |
| T-76-04 | Tampering (prototype pollution) | `queues = {}` and `loadedColumns = {}` plain objects | mitigate | Both objects are created with `const queues = {};` / `const loadedColumns = {};` (literal `{}`, not `Object.create(null)`). Index keys are integers (from server-rendered partials in Phase 77) — not user-controlled strings like `__proto__`. The module never iterates with `for...in` over inherited keys. Risk: if a future phase passes a string columnIndex equal to `'__proto__'`, no exploitation path exists because we never use `for...in` or `Object.assign` on these objects. Accept residual risk; document in CONCERNS if Phase 77 introduces dynamic indices. |
| T-76-05 | Info Disclosure | CSS custom property `--portal-initial-active-index` read | accept | The value is a column index (0, 1, 2, 3) — non-sensitive UI state. No PII. |
| T-76-SC | Supply Chain / Tampering | npm/gem installs | n/a (mitigate by absence) | Phase 76 installs ZERO new npm or gem packages — pure vanilla JS using existing browser APIs (`window.matchMedia`, `document.documentElement.style`) and existing jQuery global. RESEARCH.md "Package Legitimacy Audit" section confirms no external packages added. No supply-chain risk introduced. |

**ASVS L1 mapping:** V5 (Input Validation) — NaN-and-negative guard on `parseInt` mitigates malformed CSS property value. No V2/V3/V4/V6 categories apply (no auth, no session, no access control, no crypto).
